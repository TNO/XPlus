[[nl.esi.xtext.expressions]]
= Expressions
:lang: en

[.normal]

== Expression Language Overview

Expressions are used to compute values, make decisions, and define conditions in models. The language supports a variety of operators, function calls, and value types, and is designed to be familiar to users of modern programming and modeling languages.

*Supported value types:* bool, int, real, string, enum, record, vector, map, null.

Users can add their own types. See <<nl.esi.xtext.types>> for details.


=== Literals

* Boolean: `true`, `false`
* Integer: `42`, `-7`
* Real: `3.14`, `2.0e-5`
* String: `"hello"`, `"John Smith"`
* Null: `null`
* Enum: `TypeName::literal`
* Vector: `[1, 2, 3]` or, with an explicit type annotation, `<int[]>[1, 2, 3]`
* Record: `TypeName{field1 = value1, field2 = value2}`
* Map: `{1 -> "a", 2 -> "b"}` or, with an explicit type annotation, `<map<int, string>>{1 -> "a", 2 -> "b"}`
* Wildcard: `*` (matches any value)

=== Variables

Variables are declared with a type and a name, with optional initialization. Their values can be used in expressions:

....
int i
string s = "hello"
real x
bool flag = true
....

=== Operators

* Logical: `and`, `or`, `not` (case-insensitive: `AND`/`and`, `OR`/`or`, `NOT`/`not`)
* Comparison: `==`, `!=`, `<`, `&lt;=`, `>`, `>=`
* Arithmetic: `+`, `-`, `*`, `/`, `mod`, `^`, `max`, `min`
* Postfix: record field access `record.field`, null-safe record field access `record?.field`, map access `map[key]`, map write `map[key -> value]`

=== Function Declarations

Functions are declared using the `function` keyword, followed by an optional list of type parameters in angle brackets, a return type, a name, and a comma-separated parameter list in parentheses. Each parameter has a type and a name:

....
function ReturnType name(ParamType1 param1, ParamType2 param2)
function <T> T generic_name(T param1, T param2)
....

Examples:

....
function int sum(int[] values)
function real average(int[] values)
function string formatDate(int year, int month, int day)
function bool isValid(string input)
function <T> T get(T[] vector, int index)
function <K, V> V mapGet(map<K, V> map, K key)
....

NOTE: Function declarations define the signature only. Some implementations might be provided by a registered Java function library. See <<how-to-add-an-expression-function-library>> for details.

NOTE: Functions added via <<how-to-add-an-expression-function-library>> don't need to be declared. The framework automatically generates function declarations from registered Java methods.

=== Template/Generic Functions

Generic (template) functions allow a single function declaration to work with multiple types using type parameters. Type parameters are declared in angle brackets after the `function` keyword:

....
function <T> T get(T[] vector, int index)          // T is a type parameter
function <K, V> V mapGet(map<K, V> m, K key)      // K and V are type parameters
....

Type parameters are instantiated at each call site based on the argument types. For example:

....
int x = get(<int[]>[1, 2, 3], 0)                  // T is instantiated as int → result is int
string s = get(<string[]>["a", "b"], 0)           // T is instantiated as string → result is string
int value = mapGet(<map<string, int>>{"k" -> 42}, "k")  // K=string, V=int → result is int
....

**Automatic template generation from Java libraries**:

When a function library method uses generated DSL expression types (`ExpressionVector`, `ExpressionMap`, `Expression` — from Expressions.xtext), the framework automatically generates a template function declaration. For example:

- Java method: `Expression get(ExpressionVector v, long i)` 
  Generated: `function <T> T get(T[] p0, int p1)`

- Java method: `Expression get(ExpressionMap m, Expression key)`
  Generated: `function <K, V> V get(map<K, V> p0, K p1)`

See <<how-to-add-an-expression-function-library>> for details on template function generation from Java libraries.

=== Function Calls

Declared Functions can be called as follows:

* `function_name(args)`
* `function_name(positional_args, name = value, ...)`

....
int total = sum(v)             // calls function explicitely declared in the model
int numbers = range(1, 10, 2)  // calls a default function
....

==== Named Arguments

Function calls support named arguments, which allow specifying arguments by parameter name rather than position. Named arguments must appear after all positional (indexed) arguments:

....
function string formatDate(int year, int month, int day)

string d1 = formatDate(2026, 5, 29)                    // all positional
string d2 = formatDate(2026, month = 5, day = 29)      // mixed positional and named
....

Rules for named arguments:

* Named arguments must come after all positional arguments.
* A parameter cannot be specified both positionally and by name.
* Duplicate named arguments (same name used twice) are not allowed.
* The named argument name must match a declared parameter name.
* The total number of positional plus named arguments must match the function's parameter count.

=== Parentheses

Parentheses can be used to group expressions and control evaluation order:

....
(1 + 2) * 3
....

=== Type Annotation for Vectors and Maps

Vectors and maps can be constructed with an explicit type annotation. The type is specified in angle brackets before the value:

....
<int[]>[1, 2, 3]
<map<int, string>>{1 -> "a", 2 -> "b"}
....

The type annotation is optional: when it is omitted, the element type (resp. key and value types) is inferred from the literal's elements/pairs - the common type every element is assignable to (e.g. a shared base type for records, or `real` for a mix of `int` and `real` elements):

....
[1, 2, 3]                       // inferred as int[]
{1 -> "a", 2 -> "b"}             // inferred as map<int, string>
....

An *empty* vector/map literal (`[]`/`{}`) has no elements/pairs to infer the type from, so when no explicit annotation is given, the type is instead inferred top-down from the position the literal occurs in - e.g. the declared type of the variable it initializes:

....
int[] empty = []                    // inferred as int[] from the variable's declared type
map<int, string> emptyMap = {}      // inferred as map<int, string> from the variable's declared type
....

This top-down inference also applies to a record field's or a declared type's default value, a field's value inside a record literal, a key/value inside an explicitly type-annotated map literal, an element inside an explicitly type-annotated vector literal, and a (non-generic) function call argument.

An explicit annotation is still required for an empty literal that occurs where no such top-down type is known (e.g. a plain operand of a binary/comparison expression), and can always be added to disambiguate or to widen the inferred type regardless:

....
real[] values = <real[]>[1, 2, 3]   // forces real instead of the inferred int
....

NOTE: If the elements/pairs of a literal without an explicit annotation do not share a common type (e.g. mixing unrelated record types), validation reports an error asking for an explicit type annotation. The same applies to an empty literal for which no type - neither explicit nor inferred top-down - could be determined at all.

=== Wildcard Expression

The wildcard  *  can be used as a standalone expression to match any value. It is useful in pattern matching or as a placeholder. Note: this is different from `*` used as a multiplication operator in arithmetic expressions.

Example of wildcard usage:

....
bool result = (someValue == *)
....

=== Expression Examples

....
int x = 5 + 3 * 2           // multiplication operator
bool b = (x > 10) and not false
string s = "Hello, " + "world!"
....

=== Vectors and Records

Vectors and records can be constructed and accessed as follows:

....
int[] numbers = <int[]>[1, 2, 3]
int[] moreNumbers = [4, 5, 6]        // type annotation omitted, inferred as int[]
Person p = Person{name = "Alice", age = 30}
int n = get(numbers, 0)
string name = p.name
....

=== Maps

Maps associate keys with values. Example:

....
map<int, string> m = <map<int, string>>{1 -> "a", 2 -> "b"}
map<int, string> m2 = {1 -> "a", 2 -> "b"}  // type annotation omitted, inferred as map<int, string>
string v = m[1]
map<int, string> v2 = m[2 -> "c"]
....

=== Null Value

The `null` literal represents the absence of a value. It can be used with any type.

The nullish coalescing `??` operator is a logical operator that returns its right-hand side operand when its left-hand side operand is `null`, and otherwise returns its left-hand side operand.

----
int a = null
int b = a ?? 10 // b now holds the value 10
----

=== Ternary Expression

The conditional (ternary) operator is the only operator that takes three operands: a condition followed by a question mark `?`, then an expression to execute if the condition is truthy followed by a colon `:`, and finally the expression to execute if the condition is falsy.
This operator is frequently used as an alternative to an `if...else` statement.

`string x = flag ? "Hello" : "Goodbye"`

=== Operator Precedence

Operators are evaluated in the following order (highest to lowest):

. Parentheses and literals
. Postfix: (null-safe) record field access `record.field` or `record?.field`, map access `map[key]`, map write `map[key -> value]`
. Unary: `not`, unary `+`, unary `-`
. Power: `^` (right-associative)
. Null-coalescing: `??` (right-associative)
. Conditional (ternary): `? :` (right-associative)
. Multiplicative: `*`, `/`, `mod`, `max`, `min` (left-associative)
. Additive: `+`, `-` (left-associative)
. Comparison: `<`, `&lt;=`, `>`, `>=` (left-associative)
. Equality: `==`, `!=` (left-associative)
. Logical: `and`, `or` (left-associative, lowest precedence)

=== Notes

* Type checking is performed at model validation time.
* Functions and operators may be overloaded for different types.
* The wildcard `*` can be used as a placeholder or to match any value.
* Map write access uses the syntax `map[key -> value]`.
* Type annotation for vector and map construction is optional and can be omitted whenever the element (resp. key/value) type can be inferred from the literal's content, or - for an *empty* `[]`/`{}` literal - from the top-down position it occurs in (e.g. a variable's declared type); it is still required when neither is available. See <<Type Annotation for Vectors and Maps>>.
* Logical operators `and`, `or`, and `not` are case-insensitive and accept both lowercase and uppercase forms (e.g., `AND`, `and`, `OR`, `or`, `NOT`, `not`).
* Operator associativity: most operators are left-associative; the power `^`, null-coalescing `??` and Conditional (ternary) `? :` operators are right-associative.
* Variables can be declared with optional initialization: `Type name = expression` or just `Type name`.

NOTE: When invoking functions with custom Java types, `IExpressionConverter` instances are evaluated in order until one successfully converts the argument. The first successful conversion is used. This allows custom converters to handle specific types while falling back to default converters for built-in types. See <<how-to-add-an-expression-function-library>> for details on implementing custom converters.
